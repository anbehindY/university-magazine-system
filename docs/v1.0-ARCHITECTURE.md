## Authentication & Authorization

### Better Auth Setup

```
                      ┌─────────────────┐
                      │   Better Auth   │
                      │   (Server)      │
                      ├─────────────────┤
                      │ Email/Password  │
                      │ Session-based   │
                      │ Admin plugin    │
                      │ Database hooks  │
                      └────────┬────────┘
                               │
                ┌──────────────┼──────────────┐
                ▼              ▼              ▼
         ┌───────────┐  ┌───────────┐  ┌───────────┐
         │ API Route │  │ Server    │  │ Client    │
         │ Handler   │  │ Component │  │ Component │
         └───────────┘  └───────────┘  └───────────┘
         getSession()   getCurrentUser() useSession()
```

**5 roles with scoped access:**

| Role | Scope | Access |
|------|-------|--------|
| ADMINISTRATOR | System-wide | Manage years, users, upload rules, reports |
| MARKETING_MANAGER | All faculties, all years | View submissions, download ZIP, reports |
| MARKETING_COORDINATOR | Own faculty, active year | Review, comment, select submissions |
| STUDENT | Own submissions | Create, edit, submit, comment |
| GUEST | Own faculty, selected only | Read-only view of selected articles |

**Auth flow:**
1. Sign-in via `/api/auth/[...all]` (Better Auth catch-all)
2. Session stored in database (`session` table)
3. Each API route calls `auth.api.getSession({ headers })` to authenticate
4. Role checked inline — no middleware; each route enforces its own permissions
5. Banned users blocked at session creation via `databaseHooks.session.create.before`

## API Route Architecture

All routes are Next.js App Router API handlers (`route.ts` files). Authentication and role checks are performed at the top of each handler.

```
app/api/
├── auth/[...all]/route.ts            # Better Auth catch-all handler
├── academic-years/route.ts           # GET: public year data
├── faculties/route.ts                # GET: faculty list
├── submissions/
│   ├── route.ts                      # GET/POST/PUT/DELETE (student CRUD)
│   └── upload/route.ts               # POST: Vercel Blob file upload
├── comments/route.ts                 # GET/POST: comment threads
├── coordinator/
│   └── submissions/route.ts          # GET/PATCH: faculty submissions + selection
├── manager/
│   └── submissions/
│       ├── route.ts                  # GET: cross-faculty submissions
│       └── download/route.ts         # GET: streaming ZIP download
├── guest/
│   └── submissions/route.ts          # GET: selected articles (faculty-scoped)
├── admin/
│   ├── academic-years/route.ts       # GET/POST/PUT/PATCH/DELETE
│   ├── users/route.ts                # GET/POST/PUT (user management)

│   └── upload-rules/route.ts         # GET/PUT (config settings)

```

**Request lifecycle:**
```
Request → Auth Check → Role Check → Closure Guard → Business Logic → Response
```

## Closure Date Enforcement

The system enforces two deadlines per academic year that gate mutations:

```
  ──────────────────────────────────────────────────────────▶ Time
  │                        │                      │
  │   Open Period          │  Partial Closure      │  Full Closure
  │                        │                      │
  │  Students: create,     │  Students: edit,     │  All: read-only
  │  edit, submit, comment │  comment (no new)    │
  │  Coordinators: review, │  Coordinators: same  │
  │  comment, select       │                      │
  │                        │                      │
  ▼                        ▼                      ▼
  Year Activated     First Closure Date     Final Closure Date
```

**Implementation** (`lib/closure-guard.ts`):
- `getActiveAcademicYear()` — fetches the active year with closure dates
- `isPastFirstClosure()` — blocks new submission creation
- `isPastFinalClosure()` — blocks all mutations (edits, comments, file changes)

Guards are called at the top of mutation routes and return `403` if the deadline has passed.

## File Storage

**Provider:** Vercel Blob (cloud object storage)

```
Student Upload → Vercel Blob API → Returns URL
                                        │
                                        ▼
                              SubmissionFile record
                              (url, pathname, contentType, size)
                                        │
                                        ▼
                     Manager Download → Fetch URLs → Stream into ZIP
```

- Files uploaded via `@vercel/blob` `put()` in `/api/submissions/upload`
- Metadata stored in `SubmissionFile` table
- Configurable limits via `ConfigSetting` (max size, allowed types, max files)
- Manager ZIP download uses `archiver` to stream files into `Faculty/Student/filename` structure

## Email Notifications

**Provider:** Nodemailer with Gmail SMTP (configurable)

**Trigger:** When a student submits a submission (status changes to SUBMITTED), the system sends a fire-and-forget email to the faculty's coordinator.

```
Student Submits → API Route → sendMail() → SMTP → Coordinator Inbox
                                  │
                              (non-blocking,
                               .catch(console.error))
```

**Configuration** (environment variables):
- `SMTP_HOST` — SMTP server (e.g., `smtp.gmail.com`)
- `SMTP_PORT` — Port (587 for TLS, 465 for SSL)
- `SMTP_USER` — Email account username
- `SMTP_PASS` — App password (not account password)
- `SMTP_FROM` — Sender address

## Security Model

| Layer | Protection |
|-------|-----------|
| Authentication | Better Auth session-based with email/password |
| Authorization | Role check at every API route — no global middleware |
| Faculty isolation | Coordinators and guests scoped to their assigned faculty |
| Closure enforcement | Deadline guards block mutations after closure dates |
| User bans | Blocked at session creation, preventing sign-in |
| File validation | Configurable upload rules (size, type, count) |
| Input validation | Zod schemas on form inputs; Prisma parameterized queries |
| CSRF | Better Auth built-in CSRF protection via session tokens |

## Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| Route-level auth (no middleware) | Simpler mental model; each route is self-contained and testable |
| Prisma with native pg adapter | Required for Neon serverless PostgreSQL on Vercel |
| Better Auth over NextAuth | Built-in admin/role plugin, simpler API, better TypeScript DX |
| SWR over React Query | Lighter weight, sufficient for the app's data fetching needs |
| Vercel Blob over S3 | Native Vercel integration, zero-config, works with serverless |
| Streaming ZIP (Archiver) | Memory-efficient for large downloads; no temp file on disk |
| Fire-and-forget email | Submission response isn't blocked by email delivery |
| Academic year scoping | Submissions tied to year at creation; historical data preserved |
