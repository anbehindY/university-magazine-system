# Test Cases — v1.1

> Test cases for verifying all new features introduced in v1.1 of the University Magazine Contribution System.

**Default Password:** `password` (all seeded accounts)

## 1. Password Change Gate (Security)

### TC-PWG-01: Admin-Created User Redirected to Change Password

- **Login as:** `guest.eng@uog.com` (mustChangePassword=true)
- **Steps:** Navigate to `/sign-in` → Enter credentials → Click Sign In
- **Expected:** Redirected to `/change-password` instead of the normal dashboard or guest page.

### TC-PWG-02: Cannot Access Portal Until Password Changed

- **Login as:** `charlie.brown@uog.com` (mustChangePassword=true)
- **Steps:** After login redirect to `/change-password`, try to navigate to `/` (portal dashboard)
- **Expected:** Automatically redirected back to `/change-password`. Portal pages are inaccessible.

### TC-PWG-03: Cannot Access Guest Pages Until Password Changed

- **Login as:** `guest.eng@uog.com` (mustChangePassword=true)
- **Steps:** After login redirect to `/change-password`, try to navigate to `/guest`
- **Expected:** Automatically redirected back to `/change-password`. Guest pages are inaccessible.

### TC-PWG-04: Cannot Bypass Gate via Direct URL Navigation

- **Login as:** `guest.eng@uog.com` (mustChangePassword=true)
- **Steps:** After login, manually type various portal/guest URLs in the address bar (e.g., `/guest`, `/`, `/reports`)
- **Expected:** All attempts redirect back to `/change-password`.

### TC-PWG-05: Successful Password Change Unlocks Access

- **Login as:** `guest.eng@uog.com` (mustChangePassword=true)
- **Steps:** On `/change-password`, enter new password → Confirm new password → Submit
- **Expected:** Password updated. `mustChangePassword` set to false. User redirected to their normal landing page (e.g., `/guest` for guest role).

### TC-PWG-06: Access Normal Pages After Password Change

- **Login as:** `guest.eng@uog.com` (after password has been changed)
- **Steps:** Navigate to `/guest`
- **Expected:** Guest page loads normally. No redirect to `/change-password`.

### TC-PWG-07: Self-Registered Guest Not Redirected

- **Pre-condition:** A guest account registered via `/register` (mustChangePassword=false)
- **Steps:** Navigate to `/sign-in` → Enter self-registered guest credentials → Click Sign In
- **Expected:** Redirected to `/guest` directly. No redirect to `/change-password`.

### TC-PWG-08: Student with mustChangePassword Redirected

- **Login as:** `charlie.brown@uog.com` (mustChangePassword=true)
- **Steps:** Navigate to `/sign-in` → Enter credentials → Click Sign In
- **Expected:** Redirected to `/change-password`. Cannot access portal until password is changed.

## 2. Login Tracking / Welcome Card

### TC-LT-01: Welcome Card on Dashboard — First Login

- **Login as:** Any user logging in for the first time (no previous `lastLoginAt`)
- **Steps:** After login, view the dashboard
- **Expected:** Welcome card displays a "first login" message (e.g., "Welcome! This is your first login.").

### TC-LT-02: Welcome Card on Dashboard — Subsequent Login

- **Login as:** Any user who has logged in before
- **Steps:** After login, view the dashboard
- **Expected:** Welcome card displays the previous login timestamp (e.g., "Last login: 10 Mar 2026, 14:30").

### TC-LT-03: lastLoginAt Updates on Successful Login

- **Steps:** Note the current `lastLoginAt` for a user → Log out → Log back in → Check dashboard
- **Expected:** Welcome card shows the timestamp of the previous login (not the current one). The `lastLoginAt` value in the database is updated to the current login time.

### TC-LT-04: Failed Login Does Not Update lastLoginAt

- **Steps:** Enter incorrect password for a user → Check `lastLoginAt` in database
- **Expected:** `lastLoginAt` remains unchanged. No update on failed authentication.

## 4. Guest Registration

### TC-REG-01: Registration Form Display

- **Steps:** Navigate to `/register`
- **Expected:** Registration form displays fields for name, email, password, and a faculty select dropdown.

### TC-REG-02: Email Uniqueness Check — Existing Email

- **Steps:** Navigate to `/register` → Enter an existing email (e.g., `sarah.johnson@uog.com`) in the email field → Wait for debounce
- **Expected:** Error message displayed indicating the email is already in use.

### TC-REG-03: Email Uniqueness Check — New Email

- **Steps:** Navigate to `/register` → Enter a new, unused email → Wait for debounce
- **Expected:** No error message. Email field shows as valid.

### TC-REG-04: Successful Registration

- **Steps:** Navigate to `/register` → Fill in name, valid new email, password, and select a faculty → Click Register
- **Expected:** Registration succeeds. User is redirected to the sign-in page.

### TC-REG-05: Registered Guest Can Sign In

- **Pre-condition:** Guest registered via TC-REG-04
- **Steps:** Navigate to `/sign-in` → Enter the registered email and password → Click Sign In
- **Expected:** Login succeeds. User is redirected to `/guest`.

### TC-REG-06: Registered Guest Has GUEST Role

- **Pre-condition:** Guest registered via TC-REG-04
- **Steps:** Log in as the registered guest → Check accessible pages
- **Expected:** User has GUEST role. Can access `/guest` and `/reports`. Cannot access portal pages (`/`, `/coordinator/*`, `/admin/*`, `/student/*`).

### TC-REG-07: Registration Does Not Set mustChangePassword

- **Pre-condition:** Guest registered via TC-REG-04
- **Steps:** Log in as the registered guest
- **Expected:** No redirect to `/change-password`. Guest chose their own password during registration, so `mustChangePassword` is false.

### TC-REG-08: Coordinator Receives Email for New Guest

- **Pre-condition:** SMTP configured with real email. Coordinator for the selected faculty has a real email address.
- **Steps:** Register a new guest selecting a faculty with a coordinator → Complete registration
- **Expected:** The coordinator for that faculty receives an email notification about the new guest registration.

### TC-REG-09: Registration Validation — Missing Fields

- **Steps:** Navigate to `/register` → Leave required fields empty → Click Register
- **Expected:** Validation errors displayed for each missing required field. Registration does not proceed.

### TC-REG-10: Registration Validation — Invalid Email Format

- **Steps:** Navigate to `/register` → Enter an invalid email format (e.g., "notanemail") → Click Register
- **Expected:** Validation error for invalid email format.

## 8. Cross-Feature Scenarios

### TC-CROSS-V11-01: Full Guest Registration to Access Flow

1. **Visitor** navigates to `/register` → Fills in details with Engineering faculty → Registers
2. **Visitor** is redirected to `/sign-in` → Logs in with registered credentials
3. **Guest** lands on `/guest` (no password change redirect since self-registered)
4. **Guest** can view selected Engineering submissions and access reports
5. **Coordinator** (`tom.baker@uog.com`) receives email notification about new guest
6. **Coordinator** sees new guest in Guest List page

### TC-CROSS-V11-02: Admin-Created User Full Password Change Flow

1. **Admin** creates a new user via `/admin/users` (mustChangePassword=true)
2. **New user** logs in → Redirected to `/change-password`
3. **New user** tries to navigate to `/` → Redirected back to `/change-password`
4. **New user** changes password → Redirected to normal landing page
5. **New user** logs out → Logs back in → No password change redirect
6. **Dashboard** shows welcome card with last login timestamp

### TC-CROSS-V11-03: Audit Trail for Selection Lifecycle

1. **Coordinator** selects a submission for publication → Audit entry created
2. **Coordinator** deselects the same submission → Audit entry created
3. **Coordinator** re-selects the submission → Audit entry created
4. **Admin** views `/admin/audit` → All three entries visible in chronological order with correct old/new values

### TC-CROSS-V11-04: Login Tracking Across Sessions

1. **User** logs in for the first time → Dashboard shows "first login" message
2. **User** logs out → Logs back in → Dashboard shows previous login timestamp
3. **User** logs out → Logs back in again → Dashboard shows the second login's timestamp (not the first)

## 9. Edge Cases

### TC-EDGE-V11-01: Password Change with Weak Password

- **Login as:** `guest.eng@uog.com` (mustChangePassword=true)
- **Steps:** On `/change-password`, enter a weak/short password → Submit
- **Expected:** Validation error. Password not changed. User remains on `/change-password`.

### TC-EDGE-V11-02: Password Change — Mismatched Confirmation

- **Login as:** `guest.eng@uog.com` (mustChangePassword=true)
- **Steps:** On `/change-password`, enter a new password → Enter a different confirmation password → Submit
- **Expected:** Validation error indicating passwords do not match.

### TC-EDGE-V11-03: Duplicate Guest Registration Attempt

- **Steps:** Navigate to `/register` → Enter an email that is already registered → Complete form → Click Register
- **Expected:** Registration fails with an error indicating the email is already in use.

### TC-EDGE-V11-04: Audit Log with No Entries

- **Login as:** `sarah.johnson@uog.com`
- **Steps:** Navigate to `/admin/audit` with custom date filter set to a range with no activity
- **Expected:** Empty state displayed. No errors.

### TC-EDGE-V11-05: Analytics with No Session Data

- **Login as:** `sarah.johnson@uog.com`
- **Steps:** Navigate to Analytics page when minimal session data exists
- **Expected:** Charts render with available data. No crashes or blank page.

### TC-EDGE-V11-06: Guest Registration — Select Faculty with No Coordinator

- **Steps:** Navigate to `/register` → Select a faculty that has no assigned coordinator → Register
- **Expected:** Registration succeeds. No coordinator notification email sent (no error thrown for missing coordinator).

### TC-EDGE-V11-07: Rapid Login/Logout — lastLoginAt Consistency

- **Steps:** Log in → Log out → Log in → Log out → Log in quickly in succession
- **Expected:** `lastLoginAt` consistently reflects the previous login timestamp. No stale or incorrect values.

### TC-EDGE-V11-08: Direct Access to /change-password Without Gate

- **Login as:** Any user with mustChangePassword=false
- **Steps:** Manually navigate to `/change-password`
- **Expected:** Either the page allows an optional password change, or redirects the user away since no password change is required.
