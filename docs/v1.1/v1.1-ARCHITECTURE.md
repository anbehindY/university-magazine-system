# Architecture — v1.1

> New features and architectural changes added in v1.1 of the University Magazine Contribution System. For the base architecture, see [v1.0-ARCHITECTURE.md](../v1.0/v1.0-ARCHITECTURE.md).

## What v1.1 Adds

v1.1 introduces five capabilities on top of the v1.0 MVP:

1. **Schema migration** — AuditLog model and User security fields
2. **Security hardening** — First-login password gate, login tracking, type-safe session
3. **Audit logging** — Immutable selection change history with admin viewer
4. **Guest self-registration** — Public signup with hardcoded GUEST role and coordinator notification
5. **Admin analytics dashboard** — Active user trends and browser usage charts

## Schema Changes

### New Model: AuditLog

Immutable, append-only log of coordinator selection changes. No `updatedAt` field and no update/delete operations exist anywhere in the codebase.

```
model AuditLog {
  id         String   @id @default(uuid())
  action     String                          # e.g. "SELECTION_CHANGE"
  entityType String   @map("entity_type")    # e.g. "SUBMISSION"
  entityId   String   @map("entity_id")      # ID of affected entity
  actorId    String   @map("actor_id")       # User who performed the action
  actor      User     @relation(...)
  oldValue   String?  @map("old_value")      # Previous state (e.g. "false")
  newValue   String?  @map("new_value")      # New state (e.g. "true")
  metadata   Json?                           # Denormalized context (see below)
  createdAt  DateTime @default(now())

  @@index([createdAt])
  @@index([actorId])
  @@index([entityId])
  @@map("audit_log")
}
```

**Metadata JSON shape** (denormalized to avoid joins at read time):
```json
{
  "submissionTitle": "My Article",
  "facultyName": "Engineering",
  "studentName": "Jane Doe"
}
```

### Modified Model: User

Two fields added to the existing User model:

```
mustChangePassword  Boolean   @default(false)  @map("must_change_password")
lastLoginAt         DateTime? @map("last_login_at")
```

New relation added:
```
auditLogs  AuditLog[]
```

## New API Routes

```
app/api/
├── register/
│   ├── route.ts                  # POST: guest self-registration
│   └── check-email/route.ts     # GET: debounced email uniqueness check
├── change-password/route.ts     # POST: first-login password change
├── admin/
│   ├── audit-log/route.ts       # GET: paginated audit entries with date filtering
│   └── analytics/route.ts       # GET: active user counts + browser breakdown
└── coordinator/
    └── guests/route.ts          # GET: faculty-scoped guest list with pagination + search
```

### POST /api/register

Public endpoint for guest self-registration.

| Aspect | Detail |
|--------|--------|
| Auth | None (public) |
| Input | `name`, `email`, `password`, `facultyId` |
| Role assignment | `GUEST` hardcoded server-side, never read from request body |
| Faculty check | Validates `facultyId` exists in database before proceeding |
| Email check | Server-side uniqueness check (defense in depth) |
| Account creation | Delegates to `auth.api.signUpEmail()`, then patches role/faculty |
| Side effect | Fire-and-forget email to faculty coordinators on success |

### GET /api/register/check-email

Public endpoint for client-side debounced email uniqueness validation.

| Aspect | Detail |
|--------|--------|
| Auth | None (public) |
| Input | `?email=` query param |
| Output | `{ available: boolean }` |
| Query | Case-insensitive match against User table |

### POST /api/change-password

Authenticated endpoint for first-login password change.

| Aspect | Detail |
|--------|--------|
| Auth | Requires authenticated session |
| Input | `newPassword`, `confirmPassword` (Zod validated, min 8 chars) |
| Logic | Hashes password via `better-auth/crypto`, updates Account, clears `mustChangePassword` flag |

### GET /api/admin/audit-log

Paginated audit log viewer for admins and managers.

| Aspect | Detail |
|--------|--------|
| Auth | ADMINISTRATOR, MARKETING_MANAGER |
| Params | `page`, `pageSize` (10/25/50), `from`, `to` (date range) |
| Output | `{ entries, total, page, pageSize }` |
| Joins | Actor name included via Prisma `select` |
| Ordering | `createdAt` descending |

### GET /api/admin/analytics

Usage analytics for the admin dashboard.

| Aspect | Detail |
|--------|--------|
| Auth | ADMINISTRATOR, MARKETING_MANAGER |
| Params | `period` (7d or 30d) |
| Output | `{ activeUsers: { total7d, total30d, daily[] }, browsers[] }` |
| Active users | Unique user IDs from sessions updated within window; excludes banned users |
| Daily trend | Cumulative unique users per day across the selected period |
| Browser data | ua-parser-js parses all session user-agent strings; bots filtered via `isBot()` |
| Threshold | Browsers under 5% of total sessions grouped into "Other" |

### GET /api/coordinator/guests

Faculty-scoped guest list for coordinators.

| Aspect | Detail |
|--------|--------|
| Auth | MARKETING_COORDINATOR |
| Scoping | Coordinator's own faculty only |
| Params | `page`, `pageSize` (10/25/50), `q` (search name/email) |
| Output | `{ guests, total, page, pageSize }` |

## Security Architecture (v1.1 additions)

### Password Change Gate

Users with `mustChangePassword: true` are blocked from using the application. The gate is enforced in three independent locations:

```
                          ┌──────────────────────┐
                          │  mustChangePassword  │
                          │       = true         │
                          └──────────┬───────────┘
                                     │
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
    ┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
    │  Portal Layout  │    │  Guest Layout   │    │  requireRole()  │
    │  (server comp)  │    │  (server comp)  │    │  (API helper)   │
    │                 │    │                 │    │                 │
    │ redirect to     │    │ redirect to     │    │ returns 403     │
    │ /change-password│    │ /change-password│    │ "Password       │
    │                 │    │                 │    │  change required"|
    └─────────────────┘    └─────────────────┘    └─────────────────┘
```

- **Portal layout** (`app/(portal)/layout.tsx`): Server-side redirect before rendering sidebar
- **Guest layout** (`app/(guest)/layout.tsx`): Server-side redirect before rendering guest UI
- **requireRole helper** (`lib/auth-helpers.ts`): Returns `{ authorized: false }` with error message, blocking all role-gated API routes

### Login Tracking

```
User Signs In → Better Auth creates Session
                         │
                    session.create.after hook
                         │
                         ▼
              prisma.user.update({
                lastLoginAt: new Date()
              }).catch(console.error)
              (fire-and-forget)
```

The `lastLoginAt` timestamp is updated via a Better Auth `databaseHooks.session.create.after` hook. The update is fire-and-forget -- a failed write does not block session creation.

### Better Auth Additional Fields

Two fields configured with `input: false` to prevent client-side manipulation:

```typescript
additionalFields: {
  mustChangePassword: {
    type: "boolean",
    required: false,
    defaultValue: false,
    input: false,          // Cannot be set via sign-up or update APIs
  },
  lastLoginAt: {
    type: "date",
    required: false,
    input: false,          // Cannot be set via sign-up or update APIs
  },
}
```

The `inferAdditionalFields<typeof auth>()` plugin on the client provides type-safe access to these fields on session objects (e.g., `session.user.mustChangePassword`).

### Guest Registration Security

```
Client POST /api/register
     │
     │  body: { name, email, password, facultyId }
     │
     ▼
┌─────────────────────────────────────────┐
│  Server (route.ts)                      │
│                                         │
│  1. Validate all fields present         │
│  2. Validate facultyId exists in DB     │
│  3. Check email uniqueness (server)     │
│  4. Create user via auth.api.signUpEmail│
│  5. HARDCODE role = "GUEST"             │  ◀── Never from request body
│  6. Set facultyId, emailVerified        │
│  7. Set mustChangePassword = false      │
│  8. Notify coordinators (fire-and-forget│
└─────────────────────────────────────────┘
```

Key security properties:
- **Role hardcoding**: The GUEST role is set server-side after account creation. The request body is never inspected for a role field.
- **Faculty validation**: The `facultyId` must correspond to an existing Faculty record.
- **Email uniqueness**: Checked server-side as defense in depth (in addition to client-side debounced check).
- **mustChangePassword**: Explicitly set to `false` for self-registered guests (they chose their own password).

## Audit Log Data Flow

```
Coordinator toggles isSelected on a Submission
     │
     ▼
PATCH /api/coordinator/submissions/[id]
     │
     ├── 1. Update submission.isSelected in DB
     │
     ├── 2. Compare wasSelected vs updated.isSelected
     │       (only log if value actually changed)
     │
     ├── 3. Fire-and-forget: prisma.auditLog.create({
     │        action: "SELECTION_CHANGE",
     │        entityType: "SUBMISSION",
     │        entityId: submissionId,
     │        actorId: coordinatorUserId,
     │        oldValue: "false",
     │        newValue: "true",
     │        metadata: {
     │          submissionTitle, facultyName, studentName
     │        }
     │      }).catch(console.error)
     │
     └── 4. Return updated submission to client


Admin views audit log
     │
     ▼
GET /api/admin/audit-log?page=1&pageSize=10&from=2026-03-01&to=2026-03-10
     │
     ├── Prisma query with date range filter + pagination
     │
     ├── Joins actor.name via select (no separate query)
     │
     └── Returns { entries, total, page, pageSize }
           │
           ▼
     Audit Log Page renders table with metadata fields
     (submissionTitle, facultyName, studentName read directly from JSON)
```

## Analytics Data Flow

```
GET /api/admin/analytics?period=30d
     │
     ├── 1. Single session query: updatedAt >= 30 days ago, exclude banned users
     │       select: { userId, updatedAt }
     │
     ├── 2. Compute unique user counts:
     │       - total7d: unique userIds from sessions in last 7 days
     │       - total30d: unique userIds from sessions in last 30 days
     │
     ├── 3. Build daily cumulative array:
     │       Group sessions by UTC date → accumulate unique users per day
     │       Result: [{ date: "2026-03-01", count: 5 }, ...]
     │
     ├── 4. Browser breakdown (separate query, all sessions with userAgent):
     │       Parse each userAgent with UAParser → count browser names
     │       Filter bots via isBot() helper
     │       Group browsers < 5% threshold into "Other"
     │       Sort by count descending
     │
     └── Return { activeUsers: { total7d, total30d, daily }, browsers }
              │
              ▼
     Analytics Page
     ├── Stat cards: total7d, total30d
     ├── AreaChart: daily cumulative trend (Recharts)
     └── PieChart (donut): browser breakdown (Recharts)
```

## Key Design Decisions (v1.1)

| Decision | Rationale |
|----------|-----------|
| Immutable AuditLog (no updatedAt, no update/delete) | Audit logs must be tamper-proof; append-only ensures integrity |
| Denormalized metadata in JSON | Avoids joins at read time; audit entries remain meaningful even if related records are deleted |
| Fire-and-forget audit writes | Selection response is not blocked by logging; `.catch(console.error)` prevents unhandled rejections |
| Fire-and-forget login tracking | Sign-in latency is not affected by the `lastLoginAt` update |
| Three-layer password gate | Defense in depth: layout redirects catch UI navigation, `requireRole` catches API calls |
| `input: false` on additional fields | Prevents clients from setting `mustChangePassword` or `lastLoginAt` via Better Auth sign-up/update APIs |
| `inferAdditionalFields` on client | Provides compile-time type safety for `session.user.mustChangePassword` and `session.user.lastLoginAt` |
| Hardcoded GUEST role | Eliminates privilege escalation via request body manipulation |
| Server-side faculty validation | Prevents registration with a non-existent faculty ID |
| Debounced client-side email check | Better UX without hammering the server; server-side check remains as defense in depth |
| Cumulative daily active users | Single session query computes both 7d and 30d counts; daily array built in memory from the same data |
| Bot filtering with isBot() | Prevents automated crawlers from skewing browser analytics |
| 5% browser threshold | Groups rare browsers into "Other" for a cleaner pie chart |
| Coordinator email on guest signup | Keeps coordinators aware of new guests without requiring them to poll the guest list |
