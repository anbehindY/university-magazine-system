## New Features Overview

v1.1 adds the following features to the University Magazine Contribution System:

1. **First Login Password Change** -- Users created by an admin are forced to change their password before accessing any page
2. **Welcome Card & Login Tracking** -- All users see a welcome card on the dashboard showing their last login timestamp
3. **Audit Log** -- Coordinator selection/deselection actions are recorded and viewable by administrators
4. **Guest Self-Registration** -- External users can register as guests via a public registration page (no login required)
5. **Guest List (Coordinator)** -- Coordinators can view a read-only list of guest users registered for their faculty
6. **Analytics Dashboard (Admin)** -- Administrators can view active user counts and browser usage charts
7. **Profile / Account Settings** -- All users can update their display name and change their password from a self-service profile page

## Feature Walkthroughs

### 1. First Login Password Change

Tests the password change gate for users with `mustChangePassword: true`.

**Steps:**

1. Sign in as **guest.eng@uog.com** with password `password`
2. You are automatically redirected to `/change-password`
3. Enter a new password (minimum 8 characters) and confirm it
4. After successful change, you are redirected to the normal guest page (`/guest`)
5. Sign out and sign back in with the new password -- the password change page no longer appears

**Verify enforcement:**

- While `mustChangePassword` is true, try navigating directly to `/guest` or any other page -- you should be redirected back to `/change-password`
- Try the same with **charlie.brown@uog.com** (Student role) -- should redirect to `/change-password`, then to the student dashboard (`/`) after changing

**Edge cases:**

- Password must be at least 8 characters -- submitting a shorter password should show a validation error
- After changing the password, the `mustChangePassword` flag is cleared and subsequent logins go straight to the dashboard

### 3. Audit Log

Tests audit trail recording and the admin audit viewer.

**Steps:**

1. Sign in as a coordinator (e.g., **tom.baker@uog.com**)
2. Navigate to **Submissions** in the sidebar
3. Open a submission and toggle the "Selected for Publication" status (select or deselect it)
4. Sign out
5. Sign in as admin (**sarah.johnson@uog.com**)
6. Click **Audit Log** in the sidebar
7. Verify the audit entry shows:
   - Coordinator name (who performed the action)
   - Action type (selection or deselection)
   - Submission reference
   - Old value and new value
   - Timestamp of the action
8. Test date filtering -- use the date pickers to narrow the audit log to a specific date range
9. Verify pagination works if there are many entries

**Key behaviours:**

- Audit entries are append-only -- there is no edit or delete functionality
- Only selection/deselection actions are recorded in v1.1
- Only administrators can access the audit log page

---

### 4. Guest Registration

Tests the public guest self-registration flow.

**Steps:**

1. Navigate to `/register` (no login required -- this is a public page)
2. Fill in the registration form:
   - Name
   - Email address
   - Password (minimum 8 characters)
   - Select a faculty from the dropdown
3. Submit the form
4. On success, you are redirected to the sign-in page
5. Sign in with the newly registered credentials
6. You land on the guest page (`/guest`) with read-only access to selected submissions for the chosen faculty

**Error handling:**

- Try registering with an email that already exists (e.g., guest.eng@uog.com) -- should show an "email already registered" error
- Try submitting with missing required fields -- should show validation errors
- Try a password shorter than 8 characters -- should show a validation error

**Security verification:**

- The registered account always has the GUEST role (hardcoded server-side, cannot be manipulated)
- The registered account does **not** have `mustChangePassword` set -- no password change redirect on first login
- The registered account cannot access portal pages (dashboard, submissions, etc.) -- only the guest layout

**Coordinator notification:**

- When a guest registers for a faculty, the coordinator(s) of that faculty receive an email notification (requires real email addresses to verify)

**Key behaviours:**

- The guest list is read-only -- coordinators cannot edit or delete guest accounts
- Coordinators only see guests for their own faculty

### 6. Analytics Dashboard (Admin)

**Steps:**

### 7. Profile / Account Settings

Tests the self-service profile page for updating name and changing password.

**Steps (Portal user):**

1. Sign in as any portal user (e.g., **david.park@uog.com** -- Student)
2. Click **Settings** in the sidebar

   - Name field is editable

5. Scroll to the password change section
6. Enter current password, new password, and confirm new password
7. Submit -- a success toast appears on successful change

**Steps (Guest user):**

2. Click **Profile** in the header navigation
3. Same profile functionality as portal users at `/guest/profile`

**Error handling:**

- Enter an incorrect current password -- should show an error toast
- Enter mismatched new password and confirmation -- should show a validation error

**Verify across roles:**

## Glossary (v1.1 Additions)

| Term | Definition |
|------|-----------|
| **Audit Log** | Append-only record of coordinator selection/deselection actions, viewable by administrators |
| **mustChangePassword** | User flag set on admin-created accounts; forces password change before any other access |
| **Last Login** | Timestamp of the user's previous successful sign-in, shown in the welcome card |
| **Self-Registered Guest** | A guest account created via the public `/register` page (no admin involvement) |
| **Password Change Gate** | Middleware enforcement that redirects users with `mustChangePassword: true` to `/change-password` |
| **Active Users** | Unique users with at least one session in a given time window (7 or 30 days) |
| **Profile Settings** | Self-service page where users can update their display name and change their password; email, role, and faculty are read-only |
